# Migration Decomposition Plan (Phase 2 Schema Changes)

This plan decomposes database schema migrations into independently owned files and explicitly maps them to the **Phase 2 — Library Excellence** schema work for:

- Hash storage (`sha256`, `sha1`) on media rows.
- Metadata provenance persistence (`MetadataFieldProvenance`).
- Scan resumability checkpoints (`ScanCheckpoint`).

Reference: `docs/planning/PREMIERE_ROADMAP.md` Phase 2 ordered actions #1, #2, #3, and #8.

## 1) Version-by-version migration file split strategy

## Goals
- Replace the monolithic migration surface with one-file-per-version ownership.
- Keep each migration narrowly scoped (single concern or tightly coupled concern).
- Make upgrade-path testing deterministic and reviewable.

## Proposed layout

```text
CleverFerret/src/main/java/com/universalmedialibrary/data/local/migrations/
  MigrationRegistry.kt
  V1/
    M001_002_InitialIndexes.kt
  V2/
    M0XX_0YY_MetadataFieldProvenanceTable.kt
  V3/
    M0YY_0ZZ_ScanCheckpointTable.kt
  V4/
    M0ZZ_100_MediaItemHashColumns.kt
  common/
    SqlGuards.kt
    MigrationTelemetry.kt
```

## Strategy by version segment

1. **Pre-Phase-2 baseline versions (current production lineage)**
   - Extract existing migrations from `AppDatabaseMigrations.kt` into versioned files without changing SQL behavior.
   - Ensure registry ordering is strictly ascending and immutable.

2. **Phase 2 provenance schema version**
   - Add `MetadataFieldProvenance` table + required indexes/foreign keys.
   - Keep data movement minimal during schema step; perform heavy backfill in post-migration worker if required.

3. **Phase 2 checkpoint schema version**
   - Add `ScanCheckpoint` table + uniqueness/index constraints for resumable scan keys.
   - No destructive changes; additive only.

4. **Phase 2 hash schema version**
   - Add `sha256` and `sha1` columns to `MediaItem` (nullable initially).
   - Add indexes for both columns.
   - Schedule deferred batched backfill using WorkManager (charging + idle constraints) rather than blocking open-time migration.

5. **Post-Phase-2 cleanup versions**
   - Optional tightening migration after telemetry confirms healthy backfill (e.g., partial NOT NULL rules where safe).
   - Never combine cleanup with new feature schema in the same version.

## 2) Auto-migration candidates vs manual migration requirements

## Auto-migration candidates
Use Room auto-migrations when all of the following hold:
- Change is additive and expressible in Room schema diff.
- No data rewrite needed in-migration.
- No SQL requiring conditional guards beyond Room-generated SQL.

Likely candidates:
- Creating new additive tables (`MetadataFieldProvenance`, `ScanCheckpoint`).
- Adding simple nullable columns (`MediaItem.sha256`, `MediaItem.sha1`).
- Adding straightforward indexes that Room can generate.

## Manual migration requirements
Use manual migrations when any of the following apply:
- Backfill logic must run in a specific batched strategy.
- Compatibility guards are needed for legacy installs with schema drift.
- Reversible repair steps or custom telemetry events are required.
- Changes require SQL not generated by Room auto-migration (complex index/constraint rewrites, table copy/rename patterns).

Manual expected for Phase 2:
- Hash backfill orchestration and repair pathways.
- Any migration that emits production telemetry checkpoints/events.
- Any long-jump safety guard (older versions that may have non-canonical schemas).

## Hybrid recommendation
Use **auto-migration for DDL shape** and **manual post-migration worker/repair flows for data movement**.
This keeps startup migration fast while preserving operational control.

## 3) Verification matrix

| Scenario | Start version | Target version | Required checks | Pass criteria |
|---|---:|---:|---|---|
| Fresh install | None | Latest | Create DB from entities, run startup integrity checks | All Phase 2 tables/columns/indexes present; app reaches ready state without deferred migration errors |
| N-1 upgrade | Previous release | Latest | Apply one-step schema upgrade + run deferred workers | No migration exceptions; hash backfill begins and reports progress; provenance/checkpoint writes succeed |
| Long-jump upgrade | Supported floor (e.g., N-3 or oldest supported) | Latest | Apply chained migrations in order + deferred workers + smoke flows | Full chain succeeds; no skipped version; duplicate lookup by hash works after backfill; resumable scan uses checkpoint rows |

## Required automated coverage
- Migration tests for every `(fromVersion -> toVersion)` edge in registry.
- End-to-end upgrade tests for:
  - Fresh install.
  - N-1 -> latest.
  - Oldest-supported -> latest.
- Data invariants:
  - Provenance rows reference valid media/metadata targets.
  - Checkpoints remain unique per scan scope.
  - Hash indexes are queryable even before backfill completion (null-tolerant queries).

## 4) Rollback/repair policy for production migration failures

## Failure detection
- Emit migration telemetry at:
  - Migration start/end per version step.
  - Deferred backfill job start/progress/failure/retry.
  - Read/write failures tied to new tables/columns.
- Attach app version, DB version, device API level, and error class.

## Policy
1. **Schema-step failure at startup**
   - Block write-path features requiring new schema.
   - Enter safe-mode read-only where possible.
   - Surface non-crashing recovery prompt and retry path.

2. **Deferred hash backfill failure**
   - Keep app functional with legacy duplicate-detection fallback path.
   - Retry with exponential backoff and bounded batch size reductions.
   - Mark rows with recoverable state to avoid restarting full-table work.

3. **Telemetry threshold breach (production)**
   - Trigger server-config kill switch for new hash-index lookup pathway.
   - Keep schema intact; route to compatibility code path while repair job runs.
   - Pause further rollout until error budget returns below threshold.

4. **Repair release guidance**
   - Ship forward-only repair migrations; do not attempt destructive downgrade.
   - Include idempotent guards (`IF EXISTS`/`IF NOT EXISTS`-style behavior where supported) in manual SQL.
   - Add one-time reconciliation job to validate table/index existence and patch drift.

## Rollback stance
- **No schema downgrades in production** (forward-fix only).
- **Feature rollback is behavioral**, controlled by runtime flags and compatibility branches.
- Preserve user data first; defer non-critical enrichment (hash/provenance completeness) until stable.
